# Security review — отдалечен (споделен) vault, engine v1.20.0 / app 0.2.23

Дата: 2026-09-05. Обхват: дизайнът от ADR-0019 и реализацията му в двете репота, плюс
предложената инсталация на VPS (`deploy-central-engine-debian.md`). Всяка констатация е
проверена в кода; каквото е предположение, е отбелязано като такова.

## 1. Модел на заплахите

Активи: бележките на фирмата (git репо + Lucene индекс на сървъра), личните ключове на хората,
GitHub PAT за backup, MCP токените на агентите.

Кой може да ги нападне:

| Нападател | Какво има | Какво искаме да не може |
|---|---|---|
| Външен, без ключ | адреса на сървъра | да чете или пише каквото и да е |
| Служител с READER роля | валиден ключ | да пише; да вижда vault-ове без grant |
| Служител с EDITOR роля | валиден ключ | да администрира; да пипа чужди vault-ове |
| Бивш служител | стар ключ | достъп след revoke |
| Друг процес/акаунт на сървъра | loopback достъп | да е admin без ключ |
| Уеб страница в браузъра на служител | може да праща заявки към localhost | да чете/пише в локалния engine |
| Някой с достъп до диска на сървъра | всичко на диска | (не е защитено, виж §4) |

## 2. Какво е защитено и как (проверено)

**Идентичност и ключове**
- Ключът е 256 бита случайност (`SecureRandom`, base64url, префикс `svk_`), генериран от engine-а,
  никога избиран от човек. Brute force е практически невъзможен.
- Сравнението е constant-time (`UserRegistry.constantTimeEquals`), обхожда всички ключове; няма
  timing разлика между „грешен ключ“ и „непознат ключ“.
- Ключът се показва точно веднъж (create/rotate); `GET /users` връща само `keyRef`, а конфигът
  приема единствено референции (`file:`, `env:`, `keychain:`) — залепен ключ в конфига се отказва.
- Сървър: файлът се създава 0600 в `secrets/`; app: 0600 файл в Application Support, никога в
  UserDefaults (verifier потвърди с grep на целия app).
- Revoke/rotate действат веднага (един `UserRegistry` за interceptor и controller, атомарен reload).
  Няма рестарт, няма кеш.

**Транспорт**
- Извън loopback engine-ът отказва да стартира без TLS на двата порта и без `localAdmin=false`.
  Зад прокси TLS е на Caddy/nginx, а `localAdmin=false` е правило за оператора (документирано).
- Bearer се праща на всяка заявка и на WebSocket upgrade-а. Engine-ът няма CallLogging, така че
  токените не попадат в лог.
- Няма CORS plugin → браузърът не може да чете отговори от engine-а от чужд origin, а JSON
  POST/PUT/DELETE минават през preflight, който без CORS header пада.

**Авторизация**
- Един interceptor за всичко под `/api/` (401 → admin таблица 403 → vault read 403 → write 403).
  Той гледа каноничния път на Ktor; `//api/…` и `%75sers` отговарят 400. Маршрут без principal
  пада затворен (500), не към локалния admin.
- Списъкът с vault-ове, federated search, cross-vault backlinks, cross-vault relink и events
  потокът са филтрирани по grant. Commit-ите носят името на човека като author.
- Admin маршрутите (users, agents, vaults create/delete, backup config, secrets, update, sources
  write) са само за admin. Последният admin не може да бъде махнат при `localAdmin=false`.
- Loopback се определя само от IP адреса на socket-а, без DNS; `X-Forwarded-For` се игнорира.

**MCP (агентите)** — отделен регистър от токени, роли по vault, TLS, audit log на всяко
действие (`mcp/AuditLog.kt`). Това предхожда спринта и не е пипано.

## 3. Пропуски, подредени по тежест

1. **DNS rebinding срещу локалния engine (pre-existing, не от този спринт).** С `localAdmin=true`
   (default на всеки Mac) engine-ът приема loopback заявки без ключ. Няма проверка на `Host`.
   Страница на `evil.example`, чийто DNS се сменя на 127.0.0.1, става same-origin за браузъра и
   чете/пише в личния vault през `http://evil.example:7619/api/…`. Класическият localhost-API
   проблем. **Поправка (малка):** при `localAdmin=true` interceptor-ът да приема само
   `Host: 127.0.0.1|localhost|[::1]` (с порт); всичко друго → 403. Влиза в един ред в `AppApiAuth`.
2. **Няма audit за хората.** Агентите имат `AuditLog`; хората — само git author за писане.
   Кой какво е чел/търсил не се записва. За „централна памет на фирмата“ read audit е очакван.
   **Поправка:** същият `AuditLog` формат за `/api` с userId, метод, път, vault, статус;
   отделен файл; без тела на заявки.
3. **Няма лог на неуспешна автентикация.** 401 не се логва никъде. Ключът не може да бъде
   познат, но не можеш и да разбереш, че някой опитва, нито да блокираш IP през fail2ban.
   **Поправка:** `log.warn("auth failed from {} on {}", ip, path)`; на VPS Caddy access log +
   fail2ban върху 401.
4. **Ключовете нямат срок и не се виждат кога са ползвани.** Бивш служител = ръчен revoke от
   admin; ако admin-ът забрави, ключът е валиден завинаги. **Поправка:** `lastUsedAt` в
   `GET /users` (евтино) и по желание `expiresAt`.
5. **`GET /settings`, `/sync/config`, `/sources` показват сървърни пътища и embedder endpoint на
   всеки READER** (code review находка, отложена). Не изтича съдържание, изтича топология.
6. **`/health`, `/ready`, `/metrics` са без автентикация по дизайн.** Показват vault id-та, брой
   документи, дълбочина на опашки. На VPS се спират в прокси-то (runbook §5); engine-ът сам не
   го прави.
7. **Изброяване на vault id-та:** grant-нат vault без достъп → 403, несъществуващ → 404.
   Документирано решение (NFR-2), ниска тежест.
8. **Ключът на човек минава през admin-а.** Admin-ът вижда ключа при create/rotate и го предава.
   Приемливо за 10–15 души; при SSO (sprint 2+) отпада.
9. **App-ът само предупреждава за `http://` към не-loopback адрес**, не отказва. Хипотеза,
   непроверена: macOS ATS (Info.plist няма `NSAllowsArbitraryLoads`) така или иначе ще спре
   plain http към външен host. Ако е така, предупреждението е достатъчно; ако не, Add трябва да
   отказва.

## 4. Каквото НЕ е защитено и трябва да се знае

- **Данните на сървъра са в открит вид**: git репото, Lucene индексът, `secrets/*.key`, PAT-ът за
  backup. Root на сървъра = всичко. Мерките са извън engine-а: диск криптиране на VPS-а (обикновено
  няма при доставчика), минимум shell акаунти, `secrets/` 0700, systemd hardening от runbook-а.
- **Backup-ът в GitHub е private repo с PAT.** Компрометиран PAT = четене и презапис на историята.
  Fine-grained PAT за едно репо, Contents read/write, с изтичане; ротация от app-а през
  `POST /secrets` без токенът да минава през Mac.
- **Няма E2E криптиране.** Сървърът чете всичко по дизайн (индексира, търси, embed-ва). Ако
  съдържание не бива да е четимо от оператора на сървъра, то не принадлежи в споделен vault.
- **Секретите в бележки:** `secretScanning` е opt-in; на споделен engine го включи.
