# ADR-0019 — App API principals: people with personal keys and per-vault roles

Status: accepted
Date: 2026-09-05
Scope: shared (company) vault, sprint 1 — `docs/design-shared-vault.md`, `docs/architecture-shared-vault.md`

## Context

Until now the App API had exactly one caller: the local UI on loopback. Invariant 7 bound it to
127.0.0.1, it carried no authentication, and every mutation was authored `svod-ui <ui@svod.local>`.
Multi-machine sync (ADR-0009) let one person's machines share a vault, with the git remote's token
as the trust boundary — whoever holds the token has everything.

The requirement now is a vault that 10–15 people read and write, from their own Macs and their own
agents, through **one engine on a server**: every change attributable to a person, some people
read-only, an admin who can add and revoke people without touching the server, and the company
GitHub token never leaving that server.

## Decisions

### 1. People are principals of the App API, modelled like MCP agents
A `Principal` is `{userId, author, admin, grants: vault → READER|EDITOR}`. A `UserRegistry` maps
personal keys to principals exactly as `AgentRegistry` maps tokens to agents: immutable maps swapped
on `reload`, constant-time key comparison. `SvodConfig.users[]` persists them; `UserController`
creates/updates/deletes/rotates at runtime and reloads the registry, so a new key works on the next
call and a revoked one fails on it — no restart.

### 2. One interceptor decides who, engine-admin, and vault access
`AppApiAuth` runs on every call under `/api/`: bearer key → principal (else 401); a table of
engine-admin routes (users, agents, backup, vaults, update, sources, import, index/embedder
control) needs `admin` (else 403); every vault-scoped route resolves `?vault=` and requires a read
grant, and a non-GET requires EDITOR (else 403). Routes never re-implement this; they only ask
`principal().author` for authorship. `GET /vaults` is filtered to the caller's grants and says the
role; federated search and the WebSocket event stream drop what the caller cannot read.

### 3. Loopback without a key stays the local UI — by default
`localAdmin: true` keeps every single-user installation byte-for-byte compatible: no key, loopback,
admin, author `svod-ui`. A shared engine sets `localAdmin: false`, after which even a process on the
same host must present a key (the reverse-proxy case).

### 4. Leaving loopback requires TLS on both ports and at least one user
`host` may be non-loopback only with `appApiTls`, `mcpTls` and a non-empty `users[]`; config
validation refuses anything less. The App API serves TLS through Netty (CIO cannot), the same
keystore shape as MCP. The alternative deployment — engine on loopback behind nginx with a real
certificate and `localAdmin: false` — needs no engine TLS at all.

### 5. Keys are generated by the engine and shown once
`POST /users` returns the raw key exactly once; `POST /users/{id}/key` rotates it. The key lives in
`<config dir>/secrets/user-<id>.key` (created 0600, never chmod'ed after the fact) and config holds
a `file:` ref. `GET /users` returns refs, never keys.

### 6. Secrets for a remote engine are uploaded once
`POST /secrets {name, value}` stores a value on the engine host and returns a `file:` ref, so a
GitHub token typed in a remote UI travels once, over TLS, and then only its ref is ever sent (to
`PUT /settings/backup`). No response ever contains the value.

## Consequences

- Contract 0.29.0 → **0.30.0** (additive): `/api/v1/me`, `/api/v1/users`, `/api/v1/users/{id}`,
  `/api/v1/users/{id}/key`, `/api/v1/secrets`, `Vault.role`, documented 401/403, a bearer
  `securityScheme`.
- A commit in a shared vault is authored by the person (name + email) and committed by the host id;
  History and the conflict UI name people, not "svod-ui".
- Invariant 7 is rewritten, not dropped: *the App API is loopback-only unless it is a shared engine
  with TLS and personal keys*.
- The app must carry a key per engine and may hold several engines at once (personal vaults local,
  company vaults central) — `svod-ui-macos` 0.2.23.

## Not decided here (next ADRs)

- Replica/offline mode for a company vault (a local engine syncing against the central one with
  the person's credential, not a GitHub token).
- SSO: the principal model does not care where a key came from; an OIDC resolver is a second
  `authenticate` source, not a new model.
- Per-folder or per-note permissions — git does not give them cheaply; a separate vault does.
