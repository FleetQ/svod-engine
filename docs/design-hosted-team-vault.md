# Design — Svod като хостната услуга (скица, зависи от отговорите в requirements §4)

- Status: **Скица.** Условен е на Q1–Q8 от `requirements-hosted-team-vault.md` §4. Тук е описано
  какво следва при най-вероятните отговори (фирмен клиент, контейнер на клиент, данни в EU) и кои
  части от engine-а и app-а трябва да се пипнат при всеки вариант.
- Дата: 2026-09-06, срещу engine v1.21.0 / contract 0.31.0, app 0.2.24.

## 1. Изолация: трите варианта

| | A. Един engine, всички фирми | B. Контейнер на фирма + control plane | C. Kubernetes namespace на фирма |
|---|---|---|---|
| Как | Днешният модел: `vaults[]` + `users[]` в един конфиг | Един процес, един конфиг, един диск на клиент | Като B, но с оркестратор |
| Граница | `AppApiAuth` — един interceptor | Процес + файлова система + мрежа | + мрежови политики |
| Цена | Най-ниска | ~1 GB RAM на клиент (JVM) + диск | + оркестрация |
| Радиус при грешка | **Всички клиенти** | Един клиент | Един клиент |
| Готовност днес | Кодът е такъв | Липсва Dockerfile и провизиране | Липсва всичко от B + чарт |

**Препоръка: B.** Причината не е теоретична: при sprint 1 adversarial-verifier-ът намери два реални
байпаса точно в този interceptor (`//api/v1/users` и `/api/v1/%75sers` минаваха покрай
автентикацията и покрай admin таблицата), при напълно зелен тестов пакет. С A такава грешка отваря
всички клиенти; с B — един. При 10–50 души на клиент разликата в цената е поносима.

## 2. Форма на системата (вариант B)

```
                    ┌──────────────┐
   app / уеб  ──────►  reverse      │   рутиране по поддомейн: <tenant>.svod.<домейн>
                    │  proxy (Caddy)│   TLS терминира тук; 443 е единственият отворен порт
                    └───────┬──────┘
                            │ loopback / вътрешна мрежа
              ┌─────────────┼──────────────┐
              ▼             ▼              ▼
        engine tenant-a  tenant-b      tenant-c        (jpackage образ, systemd unit или контейнер)
          /srv/svod/a     /srv/svod/b   ...            (vault-ове + .svod индекс + secrets)
              ▲
              │ provisioning + billing + покани
       ┌──────┴────────┐
       │ control plane │  (нов компонент — не съществува)
       └───────────────┘
```

Съществуващото, което тази форма ползва наготово:
- `basePath(of:)` в `LiveSvodClient` пази префикс от reverse proxy — значи и `/<tenant>/api/...`
  работи, ако предпочетем път пред поддомейн.
- Валидацията в `SvodConfig` вече **изисква** `localAdmin:false` + TLS при не-loopback host.
- `/health`, `/ready`, `/metrics` са налични за оркестратора (метриките искат admin ключ).
- Одитът (`audit-api.log`) и `lastUsedAt` дават основата за „кой ползва колко“.

## 3. Какво трябва да се добави в engine-а

| # | Промяна | Защо | Размер |
|---|---|---|---|
| E-1 | `vaultsRoot` в конфига; `POST /vaults` да приема само `id` и да строи пътя под него | днес приема произволен абсолютен път (`VaultController.kt:42`) — при клиентски админ това е дупка | малка |
| E-2 | Dockerfile + конфиг от env/секретен файл | няма никакво контейнерно пакетиране | малка |
| E-3 | Rate limit на App API (същият token bucket като `mcp/RateLimiter.kt`, но per principal) | днес няма | малка |
| E-4 | Квоти: макс. размер на бележка, макс. размер/брой бележки на vault, отказ с 413/507 | няма | средна |
| E-5 | `/update/apply` да може да се изключи с конфиг | на сървър ъпдейтът е на systemd/образа; днес се спира само от прокси-то | малка |
| E-6 | Агент, вързан за човек: `POST /users/{id}/agents` → агент с grants ⊆ на човека, author = човека | днес `AgentIdentity` и `Principal` са два несвързани регистъра | средна |
| E-7 | Износ: `POST /vaults/{id}/export` → git bundle | днес износът е ssh + tar | средна |
| E-8 | Метрики per tenant, изнесени навън (usage за билинг) | `/metrics` е per vault и иска admin ключ | средна |
| E-9 | (само ако Q3 → вариант A) отделяне на `tenantId` във всеки принципал и във всеки маршрут | иначе изолацията остава един interceptor | голяма |

## 4. Какво трябва да се добави в app-а

| # | Промяна | Защо |
|---|---|---|
| U-1 | `createVault` към избран engine (днес винаги локален — `MultiEngineClient.swift:249`) | иначе фирменият vault се създава само по ssh |
| U-2 | Вход с покана/линк вместо ръчно поставяне на ключ | днешният поток е „админът ти праща ключа“ |
| U-3 | `importVault` / `registerSource` към отдалечен engine или ясно съобщение защо не може | днес хвърлят `notImplemented` |
| U-4 | Разделяне на `MultiEngineClient.swift` (вече е маркирано като дълг преди sprint 2b) | файлът поема цялата рутираща логика |

## 5. Control plane (нов компонент)

Минимумът, който трябва да съществува, за да е услуга, а не ръчна работа:
регистрация на фирма · пускане/спиране на engine на клиент · покани и места · план и фактура ·
usage от метриките · износ и изтриване по заявка. Нищо от това не е в двата репозитория днес.
Свързано: engine-ът остава Apache-2.0 и FleetQ-agnostic (ADR-0002 §2) — control plane-ът е отделен,
затворен компонент и **не** трябва да влиза в engine репото.

## 6. Етапи (всеки има смисъл сам по себе си)

- **Етап 0 — минаване на runbook-а веднъж.** `deploy-central-engine-debian.md` е писан преди първата
  инсталация; всяко „[непроверено]“ трябва да падне (git clone като vault, `/update/apply` зад
  прокси, systemd, Caddy, време за първи индекс). **Без това всичко останало е предположение.**
- **Етап 1 — concierge хостинг.** 1–2 фирми, ръчно провизиране, без control plane, без билинг.
  Проверява дали някой изобщо плаща и какво пита. Изисква E-1, E-2, E-5.
- **Етап 2 — повторяемо провизиране.** Скрипт/контейнер на клиент, лимити и квоти (E-3, E-4),
  износ (E-7), U-1 и U-2 в app-а.
- **Етап 3 — самообслужване.** Control plane, регистрация, билинг, usage (E-8).
- **Етап 4 — уеб клиент.** Отговорът на Q2 решава дали изобщо се стига дотук; ако да, това е
  по-голямо от етапи 1–3 взети заедно.

## 7. Рискове, записани нарочно

1. **Auth-ът е единствената граница при вариант A** — и вече е бил пробиван два пъти на зелен пакет.
2. **Apache-2.0** — всеки може да хоства същото; конкурентното предимство е операцията, не кодът.
3. **Данни и чужди GitHub токени при нас** — DPA, GDPR, процес при инцидент, а не само техника.
4. **macOS-only клиент** — ограничава пазара, докато Q2 не получи отговор.
5. **Цена на клиент** — JVM ~1 GB + индекс + ембедване; при CPU embedder първият индекс на няколко
   хиляди бележки е минути, не секунди.
6. **Без HA** — ексклузивният lock прави failover ръчна операция.
