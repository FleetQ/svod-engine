## 2. Казус: vault с друг GitHub акаунт / преместване

### 2.1 Да закача vault към друг акаунт — работи и днес, с уговорка
1. В браузъра логни се с целевия GitHub акаунт (или отвори device URL в друг профил/прозорец).
2. Settings → Sync & Backup → Connect GitHub за този vault. Repo-то се създава под този акаунт, token-ът презаписва `backup-<vault>.remote`.

Уговорка: няма избор на организация — само личен акаунт на логнатия. За repo под организация трябва `POST /orgs/{org}/repos` (не е имплементирано).

### 2.2 Преместване от акаунт A в акаунт B — без миграция на repo
Локалният clone държи **цялата история**. Затова:
1. Connect към акаунт B (създава ново празно repo).
2. Backup now / Sync now → engine-ът push-ва пълната история на канонния ref в новото repo.
3. Старото repo под A → архив или изтриване.
4. **Всяка друга машина, синкваща същия vault, трябва да бъде пренасочена** — `.remote` файлът е per машина.

Алтернатива: GitHub „Transfer repository“ (A → B), после ръчно нов token в `.remote`. Custom ref-овете `refs/svod/*` би трябвало да се пренасят с repo-то, **[непроверено]**. Първият път е по-прост и не зависи от това.

## 4. Избраният модел: централен engine + локални UI

**Как изглежда:** един Svod engine на сървър (например fleetq-01) държи компанийните vault-ове. Той единствен има GitHub remote-а (backup към org repo-то). Всеки служител пуска macOS app-а локално; app-ът има **локален engine за личните vault-ове** и е насочен към **централния engine за компанийните**. LLM агентите на хората се връзват към централния MCP порт (това вече работи отдалечено: bearer + TLS).

**Какво това опростява спрямо днешния sync модел:**
- Няма clone на всяка машина, няма CLI onboarding, няма merge между машини. Един engine = един writer.
- Едновременна редакция на една бележка вече е решена: втория запис получава 409 (`expectedRevision`), app-ът показва 3-way merge. Механизмът съществува и днес.
- Всички UI-та получават live събития по WebSocket от един engine (`file.changed`, `commit.created`); app-ът вече знае да презарежда при външна промяна (`reconcileExternalChange`).
- Sync между машини остава само за личните vault-ове (ако човек има 2 Mac-а).

**Offline (втори кръг, отговор 1):** трябва да е възможно. Затова компанийният vault има два режима на достъп, избирани per човек/машина:
- **online** — app-ът говори директно с централния engine (по подразбиране, без локално копие);
- **реплика** — локален engine държи clone и синква срещу централния (днешният sync модел, с merge и конфликти). Тук се връщат конфликтите между хора, но само за тези, които са избрали offline.
Репликата се идентифицира към централния engine със същия личен credential, не с GitHub token: хората никога не получават достъп до org repo-то. Как engine-ът обслужва git трафика на репликата е дизайн решение.

**Какво нарушава спрямо днешния engine (това е ADR-ниво промяна):**
- App API е **loopback-only без auth** (инвариант 7, `AppApiServer.kt:54-56`) с един фиксиран автор `svod-ui`. За централен engine трябва: мрежов bind, TLS, **лична идентификация на всеки потребител**, и author = човекът.
- App-ът има **един endpoint за всички vault-ове** (Settings → Connection, host/port). Трябва endpoint per vault или „профили на engine“.
- В режим online компанийният vault няма локално копие; offline се покрива само от режим реплика (по-горе), който връща sync/merge пътя за тези хора.

**Забележка за feasibility (не е дизайн):** engine-ът вече има точно този модел за агенти — token → identity (agentId, име, email) → роля (READ_ONLY/WRITE) → списък vault-ове, hot-reload без рестарт, audit log. Естественият кандидат е същият механизъм да важи и за хора през App API.

## 5. Функционални изисквания (ревизирани)

**Идентичност и достъп (централен engine)**
- FR-1. Всеки потребител има лична идентификация към централния engine (собствен token/credential; никога споделен). Компрометиран → отзовава се един човек.
- FR-2. Роли per vault за хора: `reader` (само четене и търсене) и `editor` (пише). Owner/admin управлява членовете.
- FR-3. Всеки commit носи автора-човек (име + email) и машината (committer = hostId). Агентски commit носи и агент, и човека, чийто е агентът.
- FR-4. Админ добавя/маха потребител и сменя роля без рестарт на engine-а; промяната важи от следващата заявка.
- FR-5. UI показва автора в History / Inspector / конфликти („Иван, mac-ivan, преди 3 мин“).
- FR-5a. Admin издава и отзовава лични API ключове от app-а (Settings на централния engine). Ключът се показва веднъж при създаване.
- FR-5b. Идентификацията е разширяема: първа версия API ключ, по-късно SSO (org OAuth/OIDC) без промяна на модела роли/vault-ове.

**GitHub (само на централния engine)**
- FR-6. Connect GitHub на сървъра предлага избор на owner: личен акаунт или организация, в която акаунтът има права.
- FR-7. Преместване на vault между акаунти/организации без загуба на история (§2.2 като продукт). Хората не се засягат, защото не държат clone.
- FR-8. Личните vault-ове на собственика остават на локалния му engine с личния му GitHub акаунт (per-vault remote, вече го има).
- FR-8a. GitHub remote-ът (owner/org + repo) на компанийния vault се настройва от **vault настройките в app-а**, и когато vault-ът е на отдалечен engine. Token-ът се въвежда веднъж и остава на сървъра (Secrets ref), не в app-а.

**App (локален UI)**
- FR-9. App-ът поддържа повече от един engine едновременно: локален за личните, централен за компанийните; изборът е per vault, не глобален.
- FR-10. Свързване към централен engine от app-а: адрес + личен credential; списъкът vault-ове идва от engine-а според правата на потребителя.
- FR-11. Vault switcher-ът показва кой vault откъде идва (локален / централен) и статус на връзката.
- FR-12. Търсене „във всички vault-ове“ работи и през двата engine-а (федерирано в app-а или явно „само локални“).
- FR-12a. От vault настройките се избира режим **online** или **реплика (offline)**; смяната не губи данни и не изисква терминал.
- FR-12b. Реплика: локалният engine синква срещу централния с личния credential на човека; конфликти се показват с име (FR-13).

**Колаборация**
- FR-13. Конфликт при едновременен запис се показва с името на другия човек и се резолва от app-а (днешният 3-way UI).
- FR-14. (nice-to-have) Индикатор „X редактира тази бележка“ на база отворени WS сесии.

## 6. Нефункционални
- NFR-1. Прайм директивата остава: не се губи файл, не се презаписва мълчаливо (ADR-0001).
- NFR-2. Централният App API е достъпен само по TLS и само с валиден личен credential; без credential → 401, без роля за vault → 403 (не 404, не мълчаливо default vault).
- NFR-3. GitHub token-ът на компанийното repo не напуска сървъра и не се показва в никой UI/API отговор (днешното правило за Secrets refs остава).
- NFR-4. Audit: за всеки commit и за всяко MCP повикване е видимо човек + машина + агент; audit log-ът е четим от admin.
- NFR-5. Secret scanner-ът работи за всеки запис в компанийния vault.
- NFR-6. Latency: редакция от app-а към централен engine в същия регион се усеща като локална (< 300 ms за запис).
- NFR-7. Backup на компанийния vault продължава да е една посока от централния engine към org repo-то, с текущия график (360 мин + on-change).
- NFR-8. Отзован credential спира и online достъпа, и sync-а на репликата на този човек. Локалното му копие остава (не се изтрива отдалечено), но не получава нови промени.

## 7. Оставащи отворени точки (не блокират дизайна)
- Q2' присъствие („X редактира сега“): приема се като nice-to-have; ако е „трябва“, кажи.
- Хост и admin на централния engine: решава се при deploy, не в дизайна.
- Кое ще е org repo-то на SocialScore и кога се мести: решава се, когато централният engine съществува; дотогава §8 е междинна стъпка.
- SSO доставчик (кой org OAuth/OIDC): само да не се блокира от дизайна.

## 8. Междинна стъпка за SocialScore (може днес, без нов код)
Докато централният engine не съществува, SocialScore може да мине към org repo-то на текущия локален engine:
1. С org акаунта: създай private repo в организацията и **fine-grained PAT** само за това repo (Contents: read/write).
2. Презапиши `~/Library/Application Support/Svod/backup-socialscore.remote` с `https://x-access-token:<PAT>@github.com/<org>/<repo>.git` (0600).
3. `PUT /api/v1/settings/backup?vault=socialscore` със същия `file:` ref, после `POST /backup/now`.
4. Провери с `git ls-remote` (head == `refs/svod/backup/socialscore` == `main`).
Уловка: бутонът Connect GitHub не може да избере организация (само `/user/repos`), затова стъпката е ръчна през Advanced remote. Личните vault-ове не се пипат.

## 9. Критерии за приемане
- AC-1. Двама души на две машини редактират една бележка през централния engine; вторият запис показва конфликт с името на първия; резолва се без загуба; History показва двете имена.
- AC-2. Потребител с роля `reader` получава 403 при запис и не вижда vault-ове, за които няма роля.
- AC-3. Admin отзовава credential; следващата заявка на този човек е 401, без рестарт на engine-а.
- AC-4. App-ът показва едновременно личен vault (локален engine) и компанийен (централен), превключването не губи състояние.
- AC-5. GitHub token-ът на org repo-то не се появява в нито един API отговор, лог или UI.
- AC-6. Преместване на компанийния vault от org A в org B: `git ls-remote` на новото repo показва същия head; хората не правят нищо.
- AC-7. Нов служител влиза: получава адрес + credential, въвежда ги в app-а, вижда vault-а под 5 минути, без терминал.
- AC-8. Служител превключва vault-а в режим реплика от app-а, редактира без мрежа, при връщане на мрежата промените стигат до централния engine и до другите; конфликт с друг човек се показва с име.
- AC-9. GitHub remote-ът на компанийния vault се сменя от app-а към друго org repo; следващият backup показва пълната история там; token-ът не минава през app-а.
